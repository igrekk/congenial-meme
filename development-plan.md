# Приложение учета рабочего времени

Дата концепции: 18 ноября 2026 года.

Состояние на 20 ноября 2026 года: предварительная рабочая версия реализована на Python со стандартной библиотекой, SQLite и интерфейсом HTML/CSS/JavaScript. Главный экран по пожеланию пользователя — календарь месяца с объектами и часами в каждой ячейке и подробностями дня по нажатию. Сервисы разделены по описанным ниже функциям. Предложение React/FastAPI в исходной концепции заменено вариантом без установки дополнительных библиотек. Текущий запуск и результаты проверок описаны в README.md; отчет по пользовательскому шаблону и расширенная статистика остаются следующими этапами.

Цель: быстро записывать время по проектам **INAL, INAC, GCVU, ECGP** и задачам, а затем получать проверяемые итоги за день, неделю и произвольный период.

## 1. Границы первой версии

Рабочая гипотеза для оценки: один пользователь, Windows, данные на его компьютере. Интерфейс открывается в браузере, локальная служба запускается вместе с приложением. Интернет для учета времени не требуется. Многопользовательская работа и синхронизация между устройствами — отдельные будущие решения.

**Первая рабочая версия:**

- Четыре готовых проекта.
- Создание задачи внутри проекта и возвращение к существующей задаче.
- Ручная запись: проект, задача, дата, длительность, необязательное примечание.
- Запуск, пауза, продолжение и завершение таймера.
- Автоматическое создание записи времени после завершения таймера.
- Журнал за день и обзор недели с итогами по проектам.
- Исправление и удаление ошибочных записей, архивирование задач.
- Сохранение данных после закрытия приложения, резервная копия и восстановление.

**Макет для оценки** показывает взаимодействия и демонстрационные данные. Он служит для выбора интерфейса. Локальная база, надежное восстановление таймера, установщик и печать относятся к разработке настоящего приложения; готовность макета не означает их готовность.

**Следующие версии:** печать в нужный шаблон, экспорт за период, статистика времени и выполненного объема.

## 2. Предлагаемый интерфейс

### Основной экран «Журнал»

1. Сверху — короткая форма с переключением «Внести часы / Таймер».
2. В форме — проект и задача. Задачу можно выбрать из существующих или создать.
3. В ручном режиме добавляются дата и длительность. Принимаются `2,5`, `2.5`, `02:30`; интерфейс показывает, что это 2 часа 30 минут.
4. В режиме таймера видны название задачи, прошедшее время и действия «Пауза / Продолжить / Завершить и записать».
5. Ниже — неделя: дни и отработанные часы, переход между неделями, выбор дня.
6. Для выбранного дня — записи с проектом, задачей, длительностью, источником и действиями «Продолжить работу / Изменить».
7. Рядом на широком экране — распределение времени недели по четырем проектам; на узком экране оно переносится ниже.

Ручная запись «18 ноября, 2 часа» не содержит начала и конца работы. Поэтому в первой версии график показывает количество часов по дням. Размещение такой записи на часовой сетке потребовало бы придумывать время начала. Точный календарь по часам можно добавить позже для записей с известными интервалами.

### Экран «Задачи»

Небольшой список задач с проектом, накопленным временем и кнопкой запуска таймера. Завершенная задача архивируется, сохраняя всю историю. Для повторной работы ее можно вернуть из архива.

### Будущие экраны

- **Отчеты:** период, проекты, шаблон, предпросмотр, печать или сохранение.
- **Статистика:** период, группировка по проектам/задачам/дням, затем показатели объема и времени на единицу результата.

## 3. Архитектура и небольшие сервисы

Сервисы — отдельные модули с явными интерфейсами внутри одного локального приложения. У них общие запуск, установка и база данных. Это сохраняет небольшую стоимость обслуживания и позволяет независимо развивать отчеты и аналитику.

Предлагаемая связка: **React + TypeScript** для интерфейса, **FastAPI** для локального API, **SQLite** для хранения. Конкретные версии фиксируются при начале реализации. SQLite подходит для локальных данных отдельного приложения; FastAPI позволяет разделять маршруты по модулям, React — собирать интерфейс из компонентов. Основание выбора: [React](https://react.dev/learn/thinking-in-react), [FastAPI](https://fastapi.tiangolo.com/tutorial/bigger-applications/), [SQLite](https://www.sqlite.org/whentouse.html).

```text
Интерфейс
    │
Локальный API
    ├── ProjectTaskService
    ├── TimeEntryService
    ├── TimerService ──> TimeEntryService
    ├── SummaryService
    └── StorageService ──> SQLite

Позже:
    ├── ReportService ──> TemplateAdapter
    ├── QuantityService
    └── AnalyticsService
```

| Сервис | Ответственность | Основные операции | Этап |
|---|---|---|---|
| `ProjectTaskService` | Проекты и жизненный цикл задач | Список проектов; создать, изменить, выбрать, архивировать задачу | MVP |
| `TimeEntryService` | Сохраненные факты затраченного времени | Создать вручную, исправить, удалить, получить записи за период | MVP |
| `TimerService` | Незавершенная сессия и рабочие интервалы | Запустить, приостановить, продолжить, завершить, восстановить | MVP |
| `SummaryService` | Оперативные итоги | Сумма по дню, неделе, проекту и задаче | MVP |
| `StorageService` | Схема, транзакции и резервные копии | Миграция, резервное копирование, проверка и восстановление | MVP |
| `ReportService` | Данные и выпуск отчета | Выбрать период, сформировать снимок данных, предпросмотр, экспорт | Следующая версия |
| `TemplateAdapter` | Правила конкретного шаблона | Подставить поля и таблицу, разместить итоги и подписи | Следующая версия |
| `QuantityService` | Измеримый результат работы | Определить показатель, единицу, зафиксировать объем | Следующая версия |
| `AnalyticsService` | Расширенная статистика | Доли, динамика, план/факт, часы на единицу результата | Следующая версия |

`SummaryService` и `AnalyticsService` читают сохраненные факты. Они не создают дополнительные записи времени и не прибавляют работающий таймер к уже завершенным записям.

Пример границ API: `/projects`, `/tasks`, `/time-entries`, `/timer`, `/summaries`, `/backups`. Клиент не обращается к файлу базы напрямую. Локальный сервер слушает только интерфейс loopback; удаленный доступ потребует отдельного решения.

## 4. Модель данных

| Сущность | Минимальные поля | Назначение |
|---|---|---|
| `Project` | `id`, `code`, `name`, `archived_at` | Справочник проектов; код уникален |
| `Task` | `id`, `project_id`, `title`, `description`, `archived_at`, `created_at` | Предмет работы; название не является идентификатором |
| `TimeEntry` | `id`, `task_id`, `work_date`, `duration_seconds`, `source`, `note`, `timer_session_id?`, `created_at`, `updated_at` | Завершенный факт времени за определенную дату |
| `TimerSession` | `id`, `task_id`, `status`, `timezone`, `created_at`, `finished_at?` | Одна сессия от запуска до завершения |
| `TimerSegment` | `id`, `session_id`, `started_at_utc`, `ended_at_utc?` | Непрерывный рабочий интервал между запуском/продолжением и паузой/завершением |
| `Settings` | `timezone`, параметры резервных копий, будущие правила отчета | Пользовательские настройки |

У одной задачи может быть много ручных записей и много завершенных сессий таймера. Источники записей: `manual` и `timer`. Незавершенные сессии не входят в сохраненные итоги.

Для `TimeEntry` на первом этапе достаточно даты и точной длительности. Исходные интервалы таймера сохраняются в `TimerSegment`, чтобы их можно было проверить и корректно разделить по датам.

При будущей печати создается `ReportSnapshot`: период, версия шаблона, правила округления, названия и данные на момент выпуска. Это позволит повторить ранее выпущенный отчет после переименования задачи.

## 5. Правила учета и надежности

1. **Один таймер.** Одновременно допускается одна незавершенная сессия, в том числе находящаяся на паузе. Ограничение проверяется в базе в транзакции. Для другой задачи сначала завершают текущую сессию.
2. **Пауза исключается из времени.** На паузе рабочий сегмент закрывается. Продолжение создает новый сегмент в той же сессии.
3. **Завершение атомарно.** Закрытие последнего сегмента, создание записей и изменение статуса сессии выполняются одной транзакцией.
4. **Повторный запрос безопасен.** Повторное нажатие завершения, обновление страницы или повтор запроса возвращают уже созданный результат. Уникальная связь сессии и даты защищает от дублирования записей.
5. **Закрытие окна не сбрасывает таймер.** В базе хранится начало сегмента. После открытия интерфейс восстанавливает счетчик по временным отметкам. Приостановленная сессия остается приостановленной.
6. **Сон компьютера и забытый таймер.** В первой версии текущий интервал продолжает считаться до явной остановки, включая закрытое окно и сон. При восстановлении видны время начала и возможность исправить окончание. Это поведение необходимо показать при первом использовании таймера; автоматическое исключение сна — отдельная функция.
7. **Переход через полночь.** Завершенные интервалы таймера делятся на записи по локальным календарным датам. Часовой пояс сессии сохраняется; исходные временные отметки хранятся в UTC. Начальное значение часового пояса — `Europe/Moscow`.
8. **Длительность хранится в секундах.** Счетчик интерфейса не является источником истины. Итоги считаются по сохраненным секундам; округление применяется только по выбранному правилу отображения или отчета.
9. **Ручные значения проверяются.** Задача и дата обязательны; длительность положительная. Значение одной записи не превышает 24 часов. При превышении 24 часов в сумме за дату показывается предупреждение о возможной ошибке.
10. **Пересечения.** Если интервалы известны, пересечение отображается как предупреждение. Для ручной записи без начала невозможно надежно определить пересечение. Ее не следует автоматически считать ошибочной.
11. **История сохраняется.** Архивирование проекта или задачи не удаляет записи. Удаление самой записи имеет явное действие и возможность отмены в интерфейсе.
12. **Часовой пояс влияет на даты.** Изменение настройки не переносит вручную назначенные даты. Для старых таймеров используется сохраненный часовой пояс сессии.
13. **Резервные копии согласованны.** Для открытой SQLite-базы используется механизм резервного копирования базы. Перед восстановлением создается копия текущего состояния; проверяется формат и версия схемы.

## 7. Следующая версия: отчет в нужный шаблон

Работа начинается с конкретного образца шаблона и одного заполненного примера. До их получения можно реализовать выбор периода и сбор данных, но нельзя обещать точное совпадение печатной формы.

| ID | Небольшая задача | Проверяемый результат |
|---|---|---|
| R1 | Разобрать шаблон, поля и пример заполнения | Есть карта: поле шаблона → данные приложения; известны формат бумаги, подписи и переносы |
| R2 | Зафиксировать правила периода и округления | Определены включенные даты, группировка по задачам/дням, точность часов и округление итогов |
| R3 | Реализовать модель данных отчета | Один период дает одинаковые исходные суммы в журнале и отчете |
| R4 | Сделать адаптер первого шаблона | Реальные данные заполняют образец без ручного копирования |
| R5 | Добавить предпросмотр и экспорт/печать | PDF или иной согласованный формат соответствует шаблону при печати |
| R6 | Сохранить снимок и версию шаблона | Ранее выпущенный отчет воспроизводится после изменения задач |
| R7 | Проверить короткий и длинный периоды | Пустой месяц, длинные названия, несколько страниц и месяц с переходом года корректны |

Период задается датой начала и конца включительно; готовый вариант «Месяц» выбирает соответствующие даты. Во внутреннем запросе конец преобразуется в исключающую границу следующего дня, чтобы не терять записи последней даты.

Точность учета и правила шаблона разделяются. Если требуются десятые доли часа или шаг 15 минут, исходные секунды не перезаписываются. Для округленного отчета задается единый алгоритм, чтобы суммы строк и итогов не расходились.

Ориентир для первого шаблона после получения образца: **2–5 рабочих дней**, в зависимости от формата и сложности верстки.

## 8. Следующая версия: статистика времени и объема

### Статистика времени

1. Сумма и доля времени по проектам.
2. Динамика по дням, неделям и месяцам.
3. Задачи с наибольшими затратами.
4. При необходимости — плановая трудоемкость и отклонение от нее.

Первые три показателя строятся на существующих записях; отдельный повторный ввод времени не нужен.

### Учет объема результата

Сначала определяется, что означает объем в работе пользователя: например, документы, чертежи, позиции, метры или другие единицы. Единицы имеют смысл в рамках конкретного показателя; документы и метры не складываются.

Добавляются:

- `QuantityMetric`: название показателя, единица, применимые проекты.
- `QuantityEntry`: задача, показатель, дата выполнения, количество, примечание.
- Необязательный план задачи: показатель и ожидаемый объем.

Выполненный объем фиксируется отдельным фактом результата. Запуск очередной сессии таймера не повторяет ранее указанный объем задачи. Это предотвращает двойной подсчет, если задача выполнялась несколько дней.

| ID | Небольшая задача | Проверяемый результат |
|---|---|---|
| S1 | Добавить фильтры периода и группировки | Любой показатель воспроизводится по записям журнала |
| S2 | Добавить диаграммы времени и точные значения | Суммы совпадают с отчетом при одинаковом периоде и фильтрах |
| S3 | Согласовать показатели объема и единицы | Для каждого показателя понятно, что считается завершенным результатом |
| S4 | Добавить ввод и изменение фактов объема | Повторная работа по задаче не умножает объем автоматически |
| S5 | Добавить часы на единицу и единицы в час | Обрабатываются нулевой объем и отсутствие данных; несовместимые единицы разделены |

Для показателей производительности явно фиксируются правила сопоставления времени и результата: по задаче целиком либо по выбранному периоду. Если время затрачено в одном месяце, а результат сдан в следующем, отчет не должен скрывать это различие.

Ориентир: статистика времени **2–3 рабочих дня**, учет объема и связанные показатели **2–4 рабочих дня** после уточнения единиц и правил.

## 9. Критерии приемки MVP

- Пользователь записывает 2,5 часа по INAL и задаче, видит 2 часа 30 минут на выбранную дату.
- Пользователь создает задачу GCVU, запускает таймер, делает паузу, продолжает и завершает; запись появляется автоматически, пауза исключена.
- К одной задаче можно вернуться несколько раз; история и общий итог сохраняются.
- Двойное нажатие «Завершить» не удваивает часы.
- После закрытия приложения записи остаются, незавершенная сессия восстанавливается в правильном состоянии.
- Время через полночь распределяется на правильные даты; сумма частей совпадает с исходной длительностью.
- Редактирование и удаление отражаются во всех относящихся к ним итогах.
- Итоги по проектам, дням и задачам согласованы при одинаковых фильтрах.
- Резервная копия восстанавливается и дает те же записи и суммы.
- На узком экране доступны создание записи, остановка таймера и исправление данных.

## 10. Что уточнить при оценке макета

Эти вопросы не мешают оценить предложенный интерфейс, но влияют на реализацию:

1. Достаточно ли личной локальной версии на одном компьютере?
2. Нужен ли точный интервал начала/конца при ручном вводе или достаточно количества часов за дату?
3. Должен ли сон компьютера исключаться автоматически?
4. Как выглядит обязательный шаблон месячного отчета и какие правила округления он требует?
5. Что означает «объем» для каждого проекта и в каких единицах он измеряется?
